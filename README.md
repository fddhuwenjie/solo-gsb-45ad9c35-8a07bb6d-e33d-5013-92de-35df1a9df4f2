# 陶瓷合窑装载确认台

用于陶瓷车间“合窑”前的装载登记与确认：登记待烧批次允许的**峰温闭区间**与**保温分钟闭区间**，
把批次放入某台窑的装窑草案，预览共同可用工艺区间与窑位占位，校验通过后一次性确认生成
**不可变装载清单**；随后可为已确认窑次安排**烧成时段**（带时区的开始/结束时间与拟用工艺参数），
烧成后为安排登记**实绩**（实际峰温/保温）并自动逐批判定超界。
后端 Python Flask + SQLite，前端原生 JavaScript（无构建步骤）。

## 一键启动

```bash
docker compose up --build -d
```

启动后访问：

- 地址：**http://localhost:8000**
- 端口：**8000**（宿主机 `8000` → 容器 `8000`，可在 `docker-compose.yml` 的 `ports` 中修改）

停止：`docker compose down`；数据保存在 Docker 卷 `kiln-data`（容器/服务重启后已确认清单仍保留），
如需连数据一起清除：`docker compose down -v`。

## 本地直接运行（不用 Docker）

```bash
pip install -r requirements.txt
python wsgi.py        # 或：flask --app wsgi run --host 0.0.0.0 --port 8000
```

此时 SQLite 数据库文件为 `/data/kiln.db`（需对 `/data` 有写权限）；
也可用环境变量覆盖，默认配置见 `app/db.py`。

## 使用流程

1. **登记批次**：填写批次编号、允许峰温上下限（°C）、保温分钟上下限（闭区间）。
   修改工艺范围会使批次版本 `version + 1`，此前的预览立即过期。
2. **新建草案并选窑**：系统预置两台窑 `K1`、`K2`，每台 8 个固定编号窑位（1~8）。
3. **放入批次**：为批次选择窑位加入草案，**一批占一位**；向已占位的窑位放入新批次会替换原批次。
4. **预览**：查看
   - 共同可用峰温区间（各批次峰温范围交集）；
   - 共同可用保温分钟区间（各批次保温范围交集）；
   - 每个固定窑位的占位情况；
   - 区间无交集、批次已被其他已确认窑次占用等冲突（指出冲突批次/窑位）。
5. **确认装窑**：确认请求必须携带预览时的**草案版本**与各**批次版本及窑位快照**。
   服务器在单个事务内重查全部条件：
   - 草案版本、各批次版本、各窑位与预览一致，否则返回 `409 stale`，提示刷新后重新预览，**不得按过期预览确认**；
   - 窑位不重复；
   - 峰温、保温两项区间均有交集；
   - 批次未被其他已确认窑次使用。

   任一失败都会指出冲突批次或窑位，**草案与已确认记录均不改变，也不占用部分批次**。
6. **不可变快照**：确认成功后一次写入装载清单（头 + 明细，含当时共同峰温/保温区间与各批次范围快照），
   草案置为 `confirmed`。之后再修改批次工艺范围不影响已确认清单；已确认记录无任何修改/删除入口。
7. **并发争用**：两个草案同时争用同一批次时，确认在 `BEGIN IMMEDIATE` 事务内重查，
   并由 `confirmed_load_items.batch_id` 的全局唯一约束兜底——只有一个确认能成功，另一个收到冲突提示。
8. **重启保留**：数据持久化在 SQLite 文件（Docker 卷 `/data/kiln.db`，WAL 模式），重启后已确认清单按快照正常查询。

## 烧成时段安排（页面第 ④ 栏）

对已确认窑次安排烧成时段，页面按窑和开始时间分组展示全部安排：

1. **选择窑次**：下拉框列出尚未安排的已确认窑次；选中后下方提示该窑次**确认时**的共同
   峰温/保温区间，拟用参数必须落在该区间内（以确认快照为准，不取批次后续修改的范围）。
2. **填写时间与参数**：开始、结束时间按本机时区选择，提交时自动携带时区偏移；
   开始必须早于结束（时间须先后有序）；再填拟用峰温（°C）与保温分钟。
3. **保存安排**：服务器在 `BEGIN IMMEDIATE` 事务内按数据库最新安排重查——
   - 同一窑次只能安排一次（重复安排返回 409，提示改为修改原安排）；
   - 同一台窑的时间段不得重叠（**首尾相接允许**，不同窑同时烧成也允许）；
   - 冲突时返回 409 并**指出占用窑次**及其时段；同窑并发争用同一时段只有一个能成功。
4. **修改安排**：点击安排卡片上的“修改”，时段与参数填入表单（窑次不可换），保存即更新；
   任一检查失败则原安排保持不变。点“取消修改”回到新建模式。
   已登记实绩的安排没有“修改”入口（见下节）。
5. 安排持久保存在 `firing_schedules` 表，重启后保留；只新增该表，**不改动已确认装载快照**。

## 烧成实绩登记（页面第 ④ 栏，安排卡片上操作）

烧成结束后，为已有安排登记实测结果：

1. **登记实绩**：在未登记的安排卡片上点“登记实绩”，填写**实际峰温**（°C，非负数字）与
   **实际保温分钟**（非负整数）。提交时自动携带页面读取的**安排时段与拟用参数**；
   若提交前安排已被他人修改，返回 `409 stale` 提示刷新，**不生成实绩**，刷新后按最新安排重新登记。
2. **逐批判定**：登记成功即由系统记下**登记时间**，并按该窑次**确认清单快照**中每批的
   峰温、保温闭区间逐一判定（闭区间，端点算在界内）；**超出工艺区间的实测值也如实保存**，
   超界批次在结果中标出。判定所用的区间与结果随实绩一并固化——之后修改批次工艺范围
   **不改变判定**。
3. **一次且锁定**：每个安排只能登记一次（重复登记返回 409）；登记成功后该安排**不得再修改**
   （卡片上“修改”消失，直接调用 `PUT /api/schedules/{id}` 也返回 409）。
   并发登记、或登记与排程修改交错时，在 `BEGIN IMMEDIATE` 事务内以数据库最新状态裁决，
   恰好一方成功，失败不留部分记录。
4. **查看实绩**：已登记的安排卡片点“查看实绩”，在安排旁展开登记时间、**拟用值与实测值对照**、
   逐批判定表（在界内/超界）与超界项目汇总。数据保存在 `firing_results` / `firing_result_items`
   表，重启后仍可查询。

## 超界复烧批次生成（页面第 ④ 栏，实绩判定表中操作）

实绩中某批的**峰温或保温超出工艺闭区间**时，可在该条明细旁直接填写一个**新批次编号**生成
**待复烧批次**（判定表“复烧”列；一条超界明细对应一个输入框）：

1. **继承区间**：新批次是一个普通待烧批次，其峰温、保温闭区间**继承自原窑次确认清单中该批的
   工艺闭区间快照**（即实绩判定固化时使用的区间，不取原批次后来修改的范围）；系统同时固化记录
   来源实绩明细（原批次、原窑次/窑炉/安排、登记时间、实测值与超界判定）。
2. **原批次不动**：原批次仍归属原窑次，**原确认清单与实绩判定保持原样**；新批次之后可走现有
   **草案 → 预览 → 确认 → 排程 → 实绩** 全部流程；之后再修改原批次的工艺范围**不影响**新批次。
3. **生成条件**（服务器在单个 `BEGIN IMMEDIATE` 事务内重查，任一失败整体回滚，**不留部分记录**）：
   - 只有峰温或保温**超界**的明细可生成，界内明细返回 409；
   - **每条超界明细最多生成一个**复烧批次，重复申请返回 409；
   - 新编号与已有批次重复返回 409；
   - 两个并发申请（即使编号不同）由 `refire_batches.result_item_id` 全局唯一约束兜底，
     **恰好一个成功**，败方不会留下批次或来源记录。
4. **双向查看**：实绩判定表中已生成的明细显示“复烧批次 →”，点击跳到左栏该批次；
   批次列表的“复烧来源”列对复烧批次显示来源原批次，点击展开**来源实绩明细并高亮对应行**。
5. **不可删除**：复烧批次**即使尚未确认也不能删除**（删除接口返回 409），避免来源断链；
   其工艺范围仍可像普通批次一样修改（版本递增）。数据保存在新增的 `refire_batches` 表，
   **只新增表，不改动原确认清单与实绩表**，已有数据库重启后自动建表、原有数据照常使用。

## 主要 HTTP API

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/kilns` | 窑与固定窑位 |
| GET/POST | `/api/batches` | 批次列表 / 登记 |
| PUT/DELETE | `/api/batches/{id}` | 改工艺范围（带版本，乐观锁）/ 删除未使用批次 |
| GET/POST | `/api/drafts` | 草案列表 / 新建草案 |
| GET/DELETE | `/api/drafts/{id}` | 草案详情 / 删除未确认草案 |
| PUT | `/api/drafts/{id}/items` | 批次放入窑位 `{batch_id, pos_no}` |
| DELETE | `/api/drafts/{id}/items/{batch_id}` | 移出批次 |
| GET | `/api/drafts/{id}/preview` | 只读预览共同区间、占位、冲突 |
| POST | `/api/drafts/{id}/confirm` | 携带 `{draft_version, items:[{batch_id,batch_version,pos_no}]}` 确认 |
| GET | `/api/loads`、`/api/loads/{id}` | 已确认窑次列表 / 快照详情 |
| GET/POST | `/api/schedules` | 烧成安排列表（按窑和时间排序，含 `result_id` 标记）/ 新建安排 `{load_id, start_at, end_at, peak_temp, hold_minutes}`（时间须带时区） |
| PUT | `/api/schedules/{id}` | 修改安排的时段与参数（重查失败则原安排不变；已登记实绩的安排返回 409） |
| GET/POST | `/api/schedules/{id}/result` | 查看 / 登记该安排的烧成实绩。登记体：`{start_at, end_at, peak_temp, hold_minutes, actual_peak, actual_hold}`——前四项须为页面读取的安排当前值，变动则 409 提示刷新；返回登记时间与逐批判定明细（每项含 `result_item_id` 与已生成的 `refire_batch_id/code`） |
| POST | `/api/result-items/{result_item_id}/refire` | 为一条超界实绩明细填写 `{code}` 生成复烧批次：继承确认清单中该批的工艺闭区间，返回新批次与来源实绩明细；界内明细、每条明细重复生成、编号重复、并发重复申请均 409，不留部分记录 |
| GET | `/api/batches/{id}/refire-source` | 从复烧批次追溯来源实绩明细（非复烧批次或批次不存在返回 404）。批次列表 `GET /api/batches` 对复烧批次另带 `refire_id` 与 `refire_source_*` 字段 |

过期预览确认返回示例：

```json
{ "error": "批次 B-001 的工艺范围自预览后已被修改，请刷新并重新预览后再确认", "stale": true }
```

时段重叠保存返回示例（指出占用窑次）：

```json
{
  "error": "同一台窑的烧成时段重叠，占用窑次：窑次 #1（早班合窑）2026-10-08T00:00:00.000000Z ~ 2026-10-08T04:00:00.000000Z",
  "conflicts": [
    { "schedule_id": 1, "load_id": 1, "load_name": "早班合窑",
      "start_at": "2026-10-08T00:00:00.000000Z", "end_at": "2026-10-08T04:00:00.000000Z" }
  ]
}
```
